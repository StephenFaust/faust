- 核心结论：`updateAgent` 的"必须升版本"不是 CAS（两人都从 v1 提交 v2 双双通过）；绑定与下架/删除是"双向 check-then-act"；`deleteAgent` 存在 TOCTOU；skills 条目全量替换与绑定交错会让运行时读到空条目（SKILL_NOT_FOUND）。
- 关键事实核对：工程**没有 @TableLogic，全部物理删除**；`agent_model_config`/`agent_system_prompt` 有 uk(agent_id)；`redisson-spring-boot-starter` 已在 pom 且 `CheckPointSaverConfig` 已注入 RedissonClient（无需新增依赖）；`AgentFactory` 有 2h 本地 LoadingCache 且无失效入口（下架后仍可对话）。
- 方案：三层防线（唯一索引/CAS → 分布式锁 → 运行时兜底）；`@DistributedLock` 注解 + `@Order(HIGHEST_PRECEDENCE)` 切面（必须比 @Transactional 外层，否则提交前放锁），key 规范 `faust:lock:{type}:{id}`，多锁排序 + RedissonMultiLock，lease=-1 交看门狗，wait 800~2000ms 超时抛 1043；新增错误码 1043 RESOURCE_LOCKED / 1044 LOCK_UNAVAILABLE / 1045 CONCURRENT_MODIFIED；Redis 故障写操作 fail-closed + `agent.center.lock.enabled` 开关。
- 方案强调纯 DB 方案在 REPEATABLE READ 下 takeOff 的快照读看不到并发插入的 rel，因此跨表复合写必须用锁；同时指出主从切换可能双持锁，故关键状态流转仍用 CAS 兜底。
